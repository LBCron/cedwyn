Build and deploy

  1. Triggers. A push to main on the paths above, a section push through sections-ci, or a manual run. Concurrency group with cancel-in-progress: false: a running build always finishes; newer pushes wait as one pending run.
  2. Preflight: Python compile checks and the agent-tools, evidence-hierarchy, parcel-story and Q&A tests.
  3. Fetch the tip of every branch in themes.json, then every commit pinned in sections.lock, one at a time.
  4. Assemble (tools/assemble.py), data views (tools/views.py: catalogue data to each app's own _db/view.json), apex source (tools/apex_source.py), shared assets (tools/fetch_missing.py).
  5. Rewrite links and store shared files once (tools/rewrite.py).
  6. Site root (tools/site.py): header and menu from themes.json, runtime, redirects, the agent footer, /academy/ and /library/.
  7. Self-contained pass, page journal (tools/page_journal.py), privacy scrub (tools/privacy_scrub.py).
  8. Catalogue database (tools/build_db.py) and its test.
  9. Guards: outbound-link fix then strict test, self-contained test, app-page and Q&A guards, internal-link audit (report-only), public-voice check (report-only), webapp nav stamp and check (tools/nav.py).
  10. Publish to branch site; reports go to main under reports/. Cloudflare Pages serves site.

sections-ci (.github/workflows/sections-ci.yml) runs the scope check on a section/<id> push, pins it and starts the build. On a pull request into main it fails unless the PR carries the label site-wide. Build length: not checked in this pass (the earlier guide gave 30–45 minutes).

Shared without duplication

  • Content addressing. A file that appears in several sections is stored once, at /_blob/<sha>.<ext>, and once in blobs. Each appearance is a row in locations.
  • References, not copies. A layer such as 1000 Cuts stores artifact ids. A section that needs a core record links to it or reads it from the database.
  • Served from the database. After the build, data and evidence files whose exact bytes are in the database are removed from the deploy and served from the database chunks by the service worker (/cedwyn-sw.js) and the page fallback (/_cedwyn/runtime.js with /_cedwyn/dbfs.js). Files that browsers fetch before a service worker runs stay as files.

Federation: section data and the core

Each section is the source of truth for its own data. The convention for a section's own database: the branch ships public/_db/section.sqlite, a small SQLite file with one table

CREATE TABLE records(kind TEXT, id TEXT, seq INTEGER, data TEXT,  -- data = one JSON object
                     PRIMARY KEY(kind, id));
CREATE TABLE meta(k TEXT, v TEXT);

holding every word and record the section shows (interface strings are rows too, for example kind = 'words'). The section's database works on its own and is served at /<id>/_db/section.sqlite. On every build, tools/build_db.py merges each section database into the core table section_records(theme, kind, id, seq, data) and adds graph edges: in_theme, derived_from (a record made from a core artifact) and shows (an image the record displays). The section's pages read their rows back from the core: SELECT kind, id, data FROM section_records WHERE theme = ? ORDER BY seq.

So a section owns its data, the core holds one merged copy for reading, search, graph and export, and a record that already exists in the core (an image, a document) is referenced by path or sha256, never copied into the section. Sections with live writes keep a small store of their own (see Sections). Every section can be taken out as a slice: /db/export/sections/<id>.json.gz holds its row, its own database rows and every artifact it shows (see Data export).

Why one built database rather than a live database per section: it costs nothing to serve, it cannot drift out of sync, and it stays inside the free limits of the host. Live per-section databases add servers, quota and replication with no gain at the current scale.

Graph and GraphQL

The nodes and edges tables are a ready graph for retrieval and analysis. A GraphQL schema is resolved in the browser against the same database: see API.

Data flows

  • HubSpot tasks and the Hive. HubSpot is the work register; GitHub is the versioned source; the Hive coordinates and is not a second task database. Agents read /hive/jobs.json (50 jobs listed at 08:27 UTC), take a job with POST /hive/api/jobs/claim (60-minute lease), mark the HubSpot task, do one material step with a signed changelog line, then release with a one-line note. Order: not started, in progress, waiting; then priority; then due date. The board file is hive/BOARD.json on the hive branch.
  • HubSpot mirror. An hourly job reads task metadata (no private bodies) and commits it to the projects branch; it shows at /online/hubspot/.
  • Mail into the site. A read-only pass over project mail every two hours (07:00–23:00 UK) classifies each message, adds it to the mail manifest, refreshes the dartboard roadmap on datro@dartboard, and queues candidates for the missing-records and evidence registers. Locked attachments are recorded as locked, never opened.
  • Registers. Books: /research/book-research-findings.csv (append-only; rows proposed through pull requests). Parcels: records in data/core/records/ format, added through an open pull request. Intelligence: the missing-records register on section/research. Existing rows are never edited in place; changes go through a pull request labelled catalogue-change.
  • Agent footer and versions. Every page carries one collapsed disclosure, “Page versions & agent info”: a semver change table (version, UTC date, editor, change, source) and a signing line for agents. The footer is added by tools/agent_footer.py at build and by the edge Worker for pages that lack it.
  • Version standard. docs/VERSION-STANDARD.md (1.1.0): versions are vMAJOR.MINOR.PATCH, oldest first; v0.0.1 is free; only the latest price is stored and each earlier version is £4.99 less, floor £0; an (i) button opens the version table. tools/version_audit.py checks it.

How to contribute

  1. Issue first. Search open GitHub issues; no duplicates. If none fits, open one with the problem, the approach and a checklist of acceptance criteria, then comment the scope you are taking. The GitHub Actions programme starts at issue #174.
  2. Branch. Section work goes on section/<id> or the theme branch. A change to main goes on its own branch with one pull request labelled site-wide.
  3. Record progress on the issue: files, commits, test results, blockers. Never report a step as done before it happened.
  4. No merge, deploy or data deletion without authorisation. No force-push. Do not start or cancel build-cedwyn while another run is going.
  5. Close an issue only when every acceptance item is checked on the live site.
  6. Public wording passes tools/agent_lint.py and the editing protocol at /research/editing-protocol/.
